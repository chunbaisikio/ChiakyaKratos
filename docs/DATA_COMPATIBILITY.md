# 数据兼容与发布

当前共享版使用 SQLite 保存工作区快照，浏览器保存个人偏好和断网/冲突恢复副本。早期纯本地版本的数据依然需要导出后导入。发布时必须同时考虑这两种数据来源。

## 本次升级

数据库启动时通过检查已有表和列执行增量迁移，不删除旧用户、工作区、邀请和业务记录。

- `users.passcode` 从明文迁移为 scrypt 哈希，新增 `passcode_lookup`。原口令仍可登录，用户 ID 不变。
- 密钥保存在 `${DB_PATH}.auth-key`，或由 `AUTH_LOOKUP_SECRET` 提供。数据库保存密钥指纹，缺失或不匹配时拒绝启动。
- 新增会话、站点编辑权限和配置表。已有 `admin` 获得博客 `editor` 权限；captain/member 不会获得该权限。
- `workspace_store` 新增 `revision`，旧快照的初始值为 0。共享业务数组及其嵌套字段保留，个人偏好不再作为共享内容返回。
- 旧登录缓存不含 CSRF token，需要重新登录；工作区缓存不会因此自动删除。

新版写入接口要求 `baseRevision`，缺少时返回 428，过期时返回 409。旧前端应与新版服务端一起更新。业务修改遇到冲突后保留本地备份，不自动覆盖远端；同步后可按需要人工恢复记录。

## 升级顺序与备份

1. 停止旧服务，备份完整 SQLite 数据及旧版代码。已有 WAL 文件应一并保留，或在正常关闭数据库后复制。
2. 更新本项目，在根目录运行 `npm ci` 和 `npm run build`。保持 `DB_PATH` 指向原数据库。
3. 启动新服务，使用原管理员、队长、成员口令检查登录、队伍、机制和记录。
4. 首次迁移后备份数据库及对应 `.auth-key`；如使用环境密钥，保存原值。博客另需备份 `source/` 和 `.releases/`。

哈希迁移完成后，不能直接用旧版服务操作新版数据库。需要回退旧服务时恢复升级前的完整备份；回退新版页面可以保留新版服务与数据库。数据库和密钥必须配套恢复，不能单独重新生成密钥。

Docker 部署要备份数据库卷、内容卷和发布卷。更新镜像保留已有内容卷，后台新增文章不会被镜像内初始文章覆盖。重建公开页面仅更新发布版本，不删除草稿。

相册、图片目录和处理后的照片分别保存在博客 `source/_albums/`、`source/_media/`、`source/assets/uploads/`。备份完整 `source/` 即可包含文章和相册；工作区 SQLite 备份不包含照片。移除相册中的照片不会删除图片库文件，公开内容可复用同一图片。

内容发布先在代码目录内完成构建，再移入持久化发布目录。`.releases/` 可以指向独立目录或卷；失败不会切换 `current.json`，公开页面继续使用上一版本。站点后台、FF14 模块后台和队伍工作区始终使用当前部署的代码版本，不随旧内容发布版本回退。

## 后台范围拆分

统一构建生成 `/admin/`、`/ff14/admin/`、`/ff14/oopsie/` 三个前端。升级应一次部署三个前端及服务端，发布检查也会验证三个入口完整。共用现有账号和会话，站点内容与 FF14 全局管理分别检查权限。保留旧 API 别名与内容 Hash 路由，不改工作区快照结构或清空浏览器中的草稿。

历史 FF14 管理员的站点编辑权限改为一次性兼容初始化，在 `app_settings` 记录 `migration.site-editor-roles.v1`。保留原管理员的已有权限；该标记生成后，移除站点权限不会在重启时被自动授回。首次创建管理员仍显式授予两种权限。此次只新增迁移标记，不修改业务记录。

本队“系统设置”拆为成员与邀请、数据备份、个人偏好，旧设置链接进入成员页。清除本机缓存只重新下载服务器快照，不向服务器保存空数据。站点后台与 FF14 模块后台不初始化队伍数据存储。

游戏名片配置保存在博客 `source/_data/games.json`，随持久化 `source/` 备份。后续升级只在该文件不存在时初始化名片，不用代码仓库中的初始配置覆盖后台修改。游戏名片不新增 SQLite 表，不改变 FF14 工作区数据；隐藏名片的独占上传头像不会复制到公开版本。

## 浏览器与旧数据

浏览器存储受来源（协议、域名、端口）限制。旧站和新站不是同一来源时，使用旧站的“导出数据备份”，在新工作区“数据备份”导入；不要尝试由新站直接读取旧域名的 localStorage。

保留以下原则：

- 新增业务字段提供默认值或后备读取；尤其检查嵌套数组中的老对象。
- 重命名或删除字段时提供明确的数据迁移，保留可恢复备份。
- Zustand 的浅层合并不会补齐嵌套对象，结构变化需要版本化 `migrate`。
- 保留成员、副本、队伍、记录 ID，避免旧记录丢失关联。

## 验证发布

```sh
npm run verify
```

`test/migration_check.mjs` 构造旧版明文口令数据库并验证迁移后身份和记录；`test/workflow_api_check.mjs` 覆盖隔离、会话和同时提交时的冲突。浏览器检查在临时内容库中验证草稿附件不公开、发布成功和构建失败继续提供旧版本。

实际升级还需要用已有 JSON 备份验证副本、队伍、记录和图表；使用两个独立浏览器会话检查同一工作区的连续修改及冲突提示。不要清空实际用户的浏览器存储或生产数据库来做这些测试。
